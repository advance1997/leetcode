## 2. 为什么不直接用数组或链表扫描

若用无序键值数组保存映射，每次 get(key) 都逐项比较，最坏 O(n)，连续 n 次查找可能 O(n²)。如果键范围很小且稠密，可以直接用键作数组下标，但任意 int 键包含负数和巨大范围，直接寻址空间不可接受。

哈希表先算哈希，再映射到 C 个桶中的一个，只在相应候选位置查找：

```text
整数键 key → 哈希扰动 → [0,C) 内的桶下标 → 比较真正的键 → 返回值
```

映射压缩了键空间，不可能保证不同键永远落在不同桶。冲突是正常现象，不代表算法失败，更不代表两个键相同。

## 3. 本次统一的教学接口

两个类均为 int→int 映射，不包装泛型，也不保留特殊整数作为空标记。

| 方法 | 行为 |
| --- | --- |
| put(key,value) | 新键增加映射；已有键覆盖值，size 不变；不返回旧值 |
| get(key) | 返回关联值，缺失抛 NoSuchElementException |
| containsKey(key) | 判断键是否存在 |
| remove(key) | 删除并返回旧值，缺失抛 NoSuchElementException |
| size()/isEmpty() | 有效的不同键数量、判空 |
| entries() | 独立 int[][] 快照，每行 `[key,value]`，顺序不保证 |

负数、0、Integer.MIN_VALUE、Integer.MAX_VALUE 都可作为键和值；-1 也可以是有效值，不能兼作“缺失”。数组快照的行也独立于内部状态。两个类都非线程安全，缺失 get/remove 不改变内容。

## 4. 哈希函数与桶下标

本实现采用固定的教学公式：

```java
int hash = key ^ (key >>> 16);
int index = hash & (capacity - 1);
```

容量始终是非零二次幂，因此位掩码得到合法非负下标。右移 16 位把高位信息混到低位，降低部分低位分布不佳的影响，但不是防碰撞保证，也不是密码学哈希。

不要用 `Math.abs(key) % capacity` 来笼统解决负数：`Math.abs(Integer.MIN_VALUE)` 仍为负数。本实现无需取绝对值。若容量不是二次幂，不能直接套用同一个位掩码公式。

容量为 4，键 1、5 的扰动结果仍分别为 1、5，二者都映射到下标 1：

```text
链地址：桶 1 → [5:50] → [1:10] → null
线性探测：槽位 1 保存 [1:10]，槽位 2 保存 [5:50]
```

完整键比较仍不可省略。Java 对象键还涉及 equals/hashCode 契约，见后文；本次 int 键用 == 比较。

## 5. 负载因子与扩容思路

设 n 为有效映射数，C 为容量，负载因子 α=n/C。容量小而键多，链变长或探测变长；扩容用额外空间换较短查找路径。它不保证恶意冲突消失。

链地址法以 0.75 为本实现阈值；线性探测对聚集更敏感，本实现把有效负载限制为 0.5，并额外监控包含墓碑的占用率。阈值是实现策略，不是所有哈希表必须使用的常数。

容量改变后，`hash & (C-1)` 也改变，所以不能只复制到相同物理位置。每个有效项必须按新规则重新定位。几何扩容减少频繁重建；对已有键仅更新值时，无需为它扩大容量。

## 6. 平均、均摊和最坏不能混写

| 维度 | 链地址法 | 线性探测法 |
| --- | --- | --- |
| 良好分布、受控负载下查询/删除 | 期望 O(1) | 期望 O(1) |
| 加入并考虑扩容/重建 | 期望均摊 O(1) | 期望均摊 O(1)，还需计入墓碑整理 |
| 极端冲突的单次普通查找 | O(n) | O(C)，C 为容量 |
| 重建 | O(C+n)，直接重新接链 | 期望 O(C+n)，极端聚集可为 O(C+n²) |
| 总存储 | O(C+n)，含节点 | O(C)，含键、值、状态数组 |
| 快照 | O(C+n) 时间、O(n) 返回空间 | O(C) 时间、O(n) 返回空间 |

“期望”依赖键及哈希分布假设，本次固定扰动不提供针对任意输入的概率保证；“均摊”分摊一串操作中的扩容等成本，不是每次都常数时间。删除不缩容，大量删除后 C 可能远大于 n，扫描全部槽位不能再简写成 O(n)。

## 7. 两种方案与其他变体的取舍

链地址法容易局部删除，不需要墓碑，但有对象和 next 引用开销，严重冲突时链表退化。线性探测数组紧凑、局部性较好，但相邻冲突会形成连续簇，失败查询和删除策略更敏感。

二次探测用不同步长减少连续聚集，却必须设计容量与探测公式以保证可用槽位能被访问。双重哈希使用第二个哈希决定步长，步长与容量需满足遍历要求。这些不是“换个公式就自然正确”，后续扩展应单独实现和验证。

## 8. Java 标准容器和常见误区

实际 Java 开发通常使用 HashMap<K,V>；HashSet<E> 适合只记录成员是否存在，计数和键值关联通常用 Map。需保持插入或访问顺序时考虑 LinkedHashMap，需按键有序时考虑 TreeMap；它们不是同一语义。

对象键必须满足：equals 相等的对象 hashCode 必须相等，反过来不成立。插入后修改影响 equals/hashCode 的字段可能使对象按新哈希找不到原位置。对象键的比较应使用正确的 equals 语义，不能照抄整数的 ==。

HashMap.get 缺失时返回 null，而且 HashMap 允许 null 值，所以必要时用 containsKey 区分；本次 int 教学接口使用异常，契约不同。HashMap 的红黑树桶是特定实现机制，不意味着本次链地址类有树化，也不能笼统宣称所有哈希操作最坏 O(log n)。并发读写应使用合适的并发容器或同步策略。
