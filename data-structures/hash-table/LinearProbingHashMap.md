# 线性探测哈希表（LinearProbingHashMap）

[总览](HashTable.md) · [Java 实现](../../src/learning/datastructures/hashtable/LinearProbingHashMap.java)

## 1. 不建冲突链，沿数组继续寻找

先计算起始槽位 h，发生冲突就访问 h+1、h+2……到数组末尾后回到 0。容量是二次幂，后继用 `(index+1)&(C-1)` 计算。

使用三个并行数组 keys、values、states；状态独立于键值，允许 0、-1、最小整数作为真正数据。

| 状态 | 含义 | 查找行为 | 插入行为 |
| --- | --- | --- | --- |
| EMPTY | 当前探测历史中未占用的槽位 | 可以停止，键不存在 | 可写 |
| OCCUPIED | 有效映射 | 比较完整键 | 不同键继续 |
| DELETED | 删除标记，也称墓碑 | 不能停止，继续探测 | 确认键不存在后可复用 |

size 统计 OCCUPIED 数量；used 统计 OCCUPIED+DELETED 数量。删除只减少 size，不减少 used，因为墓碑仍占据探测路径。

## 2. 查找与冲突示例

容量 4，插入 1→10、5→50。两个键起点都是 1：

```text
槽位：   0       1        2        3
状态： EMPTY  OCCUPIED OCCUPIED  EMPTY
映射：          1:10     5:50
```

get(5) 比较槽位 1 的完整键，发现不同，再检查槽位 2 命中。get(9) 起点也是 1，经过 1、2 后遇到槽位 3 的 EMPTY，证明当前路径没有键 9，抛缺失异常。每次查找还限制最多检查 C 个槽位，避免无限回绕。

为什么遇到 EMPTY 可以停止？某键插入时不会越过一个可用空槽位继续占据后方，且删除从不把历史占用位置改成 EMPTY。于是有效键的起点到实际位置之间不会出现 EMPTY。

## 3. 删除为什么不能直接清空

删除上图的键 1 后：

```text
正确： EMPTY | DELETED | 5:50 | EMPTY
错误： EMPTY | EMPTY   | 5:50 | EMPTY
```

正确方案 get(5) 越过墓碑仍能找到 50；错误方案会在原槽位 1 提前停止，错误报告 5 不存在。源码清除 keys/values 的旧值只是便于观察，状态仍为 DELETED，因此整数 0 与删除状态完全不同。

## 4. 插入不能在第一个墓碑就忽略后续重复键

删除 1 后 put(5,55)，如果直接在槽位 1 写入，会和槽位 2 的旧键 5 重复，size 错误增加。

本实现采用易理解的两阶段方案：

1. findIndex 先沿完整探测路径查询已有键，找到就更新值并返回。
2. 仅当确认不存在时，按容量策略决定重建，再从起点寻找第一个非 OCCUPIED 槽位写入。

这样可能扫描两遍，但在良好分布下仍是常数级预期成本，逻辑更清楚。复用墓碑时 used 不变，写入 EMPTY 时 used++；无论哪种，新键都 size++。

## 5. 两种负载指标与重建策略

有效负载限制为 0.5，加入新键之前：

- 若 size 已达到 C/2，翻倍容量后重建。
- 否则若 used 已达到 3C/4，按原容量重建，清除墓碑。
- 否则直接复用可用槽位。

覆盖已有键在此判断之前返回，因此不触发重建。有效项不超过一半，始终有非占用槽位，插入扫描可以终止；used 控制非 EMPTY 数量，避免失败查询被长历史墓碑链拖累。

容量 4 的墓碑整理完整追踪：

| 操作 | size | used | 状态要点 |
| --- | --- | --- | --- |
| put(0,10)，remove(0) | 0 | 1 | 槽 0 墓碑 |
| put(1,11)，remove(1) | 0 | 2 | 槽 0、1 墓碑 |
| put(2,12)，remove(2) | 0 | 3 | 槽 0、1、2 墓碑 |
| put(3,13) | 1 | 1 | 插入前原容量重建，墓碑清空，再占用槽 3 |

有效负载低不代表查询一定快，used 才能揭示墓碑累积。重建只迁移有效项，不复制 DELETED。删除本身不触发 O(C) 扫描；整理延迟到下一次新键 put。

## 6. 回绕和扩容

容量 4 时键 3 与 7 起点均为 3，分别落在 3 与 0，说明探测链可以跨越数组边界。

此时 size=2，再插入 11，先扩到 8。重新算起点后 3 起于 3、7 起于 7；11 起于 3，冲突后落在 4。扩容必须重新探测，不能保留原物理位置，否则查询公式和存储位置会不一致。

重建先创建新数组，在新容量中逐项重新插入，最后统一替换内部数组并令 used=size。即便容量不变，删除标记也被移除。容量上限为 1<<30，触及半容量有效负载上限时拒绝新键，允许已有键更新；实际内存仍可能更早不足。

## 7. 正确性说明

不变量：每个有效键唯一，且从其起始位置到实际位置的探测路径上没有 EMPTY。查找可在 EMPTY 安全停止；删除仅变为 DELETED，不破坏其余键的路径；插入先查重，确认缺失后使用首个可用位置，保持唯一性；重建按新公式重新插入所有有效键，恢复相同映射集合及无墓碑状态。

size、used 的更新分别对应有效项与非 EMPTY 槽位变化。查找最多扫描 C 次；插入时至少半数槽位非 OCCUPIED，迁移时也保持足够空位，因此都能结束。并发修改会破坏这些推理的前提，本类不支持并发使用。

## 8. 复杂度、聚集与替代方案

n 为有效项数、C 为容量。良好哈希分布与受控有效/墓碑负载下，查询删除期望 O(1)，普通加入期望 O(1)。几何扩容和按阈值整理分摊到一串操作后，加入期望均摊 O(1)。一次整理后墓碑为零，需要积累相应数量的新占用/删除才能再次达到阈值。

普通探测最坏 O(C)。重建扫描旧数组，并把 n 个有效键重新探测：期望 O(C+n)，若全部落入同一个起点，逐项插入可能比较 1+2+...+n 次，最坏 O(C+n²)。所以不能照搬链地址迁移始终线性的结论。

相邻冲突会形成连续簇，后续键更容易加入同一簇，这叫主聚集。线性探测缓存局部性较好，但即使负载不高，也不能保证特定恶意键集合快速。二次探测、双重哈希可改变探测路径，但必须证明覆盖和终止；本次没有实现这些扩展。

删除还可以采用后移修复探测簇，免去墓碑，却增加删除时的搬移与条件判断。本次选择墓碑加重建，便于展示“删除不能截断查找路径”。

存储 O(C)，不缩容；快照扫描容量，时间 O(C)、返回空间 O(n)。重建还需要 O(C) 量级新数组，删除后即使 n 很小也不应把表扫描成本写成 O(n)。

## 9. 运行示例

在仓库根目录执行，普通 JDK 可用 javac：

```bash
build_dir=$(mktemp -d /tmp/linear-map.XXXXXX)
java -m jdk.compiler/com.sun.tools.javac.Main -encoding UTF-8 \
    -d "$build_dir" src/learning/datastructures/hashtable/LinearProbingHashMap.java
java -cp "$build_dir" learning.datastructures.hashtable.LinearProbingHashMap
```

main 与链地址实现执行相同映射操作，预期：

```text
2
11
11
50
false
-1
```

重复 put 保持 size=2；删除 1 后仍能找到 5；最小整数键与值 -1 都合法。
