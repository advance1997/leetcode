## 1. 题目描述与约束

给定字符串 s 和 t，判断 t 是否是 s 的字母异位词。如果两个字符串包含的字符及每个字符的数量完全一致，只是排列顺序可能不同，就满足条件，返回 true；否则返回 false。

“顺序可能不同”不意味着必须不同：`"abc"` 与 `"abc"` 也满足条件。

```text
1 <= s.length, t.length <= 5 × 10^4
s 和 t 只包含小写英文字母 a～z
```

原题示例：

| s | t | 输出 | 解释 |
| --- | --- | --- | --- |
| `anagram` | `nagaram` | true | 两串都有 3 个 a，n、g、r、m 各 1 个 |
| `rat` | `car` | false | 前者有字母 t，后者有字母 c |

进阶：如果输入包含 Unicode 字符，需要怎样调整？见后文讨论，当前 Java 实现针对原题小写英文字母版本。

## 2. 先把题意转换为判断条件

本题不关心字符在哪个位置，只关心每个字符有多少个。可以把字符串理解成一袋字母：打乱袋中字母的排列，袋中的数量不会变。

```text
"aab"：{a × 2, b × 1}
"aba"：{a × 2, b × 1}  → 可以重排得到，true
"abb"：{a × 1, b × 2}  → 字母种类相同，数量不同，false
```

由此得到两个观察：

1. 长度不同一定不是异位词，因为总字符数不同。
2. 长度相同只是必要条件，还必须逐种字母比较数量。

只用 Set 判断字符种类会丢失重复次数；只比较字符编码总和也不可靠，例如 `"ad"` 和 `"bc"` 的编码和相等，但不是异位词。这里需要准确的频次信息。

## 3. 暴力解法：给每个字符找一个未使用的伙伴

先从最直观的办法出发：对于 s 中的每个字符，遍历 t，找到一个尚未被使用的相同字符。如果找不到，返回 false；全部找到则返回 true。

需要 `boolean[] matchedPositions` 标记 t 中每个位置是否被占用，否则 s 中多个相同字符可能重复使用 t 中同一个位置。

```text
如果 s、t 长度不同：返回 false
matchedPositions 全部初始化为 false

对于 s 中的每个字符：
    从左向右扫描 t
    如果某位置没有被用过，并且字符相同：
        标记这个位置，结束本次扫描
    如果扫描结束仍没找到：返回 false

返回 true
```

用 `s = "aab"`、`t = "aba"` 追踪：

| 当前 s 字符 | 搜索 t 的过程 | 匹配位置 | 标记结果 |
| --- | --- | ---: | --- |
| 第一个 a | 位置 0 的 a 尚未使用 | 0 | `[true, false, false]` |
| 第二个 a | 位置 0 已使用；位置 1 是 b；位置 2 是 a | 2 | `[true, false, true]` |
| b | 跳过位置 0，在位置 1 找到 b | 1 | `[true, true, true]` |

为什么这种选择不会破坏后续匹配？相同字符的位置可以互换，挑选其中任意一个未使用位置只会消耗该字符的一份数量，不会占用另一种字符的机会。

代码对应 `isAnagramBruteForce`。对于等长字符串，最坏时间 O(n²)，标记数组占 O(n) 额外空间。例如全部由 a 组成时，第 i 轮仍要重新跳过此前已占用的位置，扫描次数累积为 `1 + 2 + ... + n`。

## 4. 优化的思维过程：不关心位置，就不必反复寻找位置

暴力算法的瓶颈是：每处理一个字符，都从头寻找一个可用位置。

但我们最终返回布尔值，并不需要输出匹配位置。对于 a 而言，具体用掉第几个 a 没有区别，只要还有可用的 a 即可。因此可以把一批“可用位置”压缩成一个“剩余数量”。

可以把 s 当作库存，t 当作待领取清单：

- 先统计 s，得到每种字母的库存。
- 每读到 t 的一个字母，就扣减对应库存。
- 某种库存变为负数，说明领取数量超过拥有数量，立即失败。

这与上一题的联系是“保存已知信息，减少重复查找”，区别是：

| 题目 | 需要保存的信息 | 原因 |
| --- | --- | --- |
| 两数之和 | 数字 → 下标 | 最后需要返回位置 |
| 有效的字母异位词 | 字母 → 剩余数量 | 最后只需判断数量是否相等 |

## 5. 为什么这里用数组，而不必用 HashMap？

原题只有 26 个小写英文字母，并且字符编码连续，可以建立固定映射：

```text
字母：    a   b   c   ...   z
下标：    0   1   2   ...  25
映射：    字母 - 'a'
```

例如 `'c' - 'a' = 2`，访问 `remainingCounts[2]` 就能读写 c 的库存。

这是一个直接寻址的频次表，没有哈希冲突，也不需要键值装箱或哈希节点。字符范围固定且很小时，它比通用 HashMap 更直接。

如果字符集合较大或不连续，就需要重新评估映射或其他表示方式。不能把“字符串计数”一律写成长度 26 的数组。

## 6. 完整图解：从统计库存到逐个抵消

使用 `s = "aab"`、`t = "aba"`。下图只展示 a、b、c 三个槽位，其余 23 项均为 0；箭头表示当前正在读取的字符。

```text
阶段一：统计 s 的全部库存

s = a a b        初始 [a:0, b:0, c:0]
    ↑            读 a [a:1, b:0, c:0]
      ↑          读 a [a:2, b:0, c:0]
        ↑        读 b [a:2, b:1, c:0]

阶段二：按 t 逐个扣减

t = a b a        初始 [a:2, b:1, c:0]
    ↑            扣 a [a:1, b:1, c:0]
      ↑          扣 b [a:1, b:0, c:0]
        ↑        扣 a [a:0, b:0, c:0]

所有字符都成功领取，返回 true。
```

对应代码状态：

| 阶段 | 当前字符 | letterIndex | a 余量 | b 余量 | 结论 |
| --- | --- | ---: | ---: | ---: | --- |
| 统计 source[0] | a | 0 | 1 | 0 | 继续统计 |
| 统计 source[1] | a | 0 | 2 | 0 | 继续统计 |
| 统计 source[2] | b | 1 | 2 | 1 | 库存建立完成 |
| 扣减 target[0] | a | 0 | 1 | 1 | 非负，继续 |
| 扣减 target[1] | b | 1 | 1 | 0 | 非负，继续 |
| 扣减 target[2] | a | 0 | 0 | 0 | 遍历结束，true |

失败示例 `s = "aab"`、`t = "abb"`：

```text
初始库存          [a:2, b:1]
扣减第一个 a      [a:1, b:1]
扣减第一个 b      [a:1, b:0]
扣减第二个 b      [a:1, b:-1] → 库存不足，立即返回 false
```

a 还剩一个也不能帮助匹配 b，不同字母的库存不能相互替代。

## 7. 操作顺序、正确性与终止

### 为什么先统计完整的 s，再读取 t？

这样进入扣减阶段时，库存已经完整。余量变负就表示真正不足，后面不可能再有 s 中的字母来补货。

如果改为同一轮同时统计 `s[i]`、扣减 `t[i]`，中途负数不一定代表失败。例如 `s = "ab"`、`t = "ba"`，第一轮 b 的差值会暂时是 -1，但下一轮会恢复为 0。同步增减也能做，但应该在结束后检查全部差值，不能照搬当前的提前失败条件。

### 循环不变量

处理完 t 的前 k 个字符后，对于任意字母 c：

```text
remainingCounts[c]
    = c 在 s 中的总次数 - c 在 t 的前 k 个字符中的次数
```

初始 k 为 0，库存来自 s 的完整统计，因此成立。每读入一个字符，只扣减该字符对应的一项，等式仍成立。

### 为什么负数可以立即返回 false？

负数说明 t 的已读部分使用该字符的次数已经超过 s 中总次数。后续只会继续扣减，不会增加库存，所以不可能最终相等。

### 为什么最后可以不扫描 26 项是否全零？

前面已经保证两串等长。统计 s 一共加 n 次，遍历 t 一共减 n 次，最终所有计数的总和为 0。

如果已经排除了负数，则每项都非负。非负数的总和为 0，只可能每一项都为 0。因此频次完全相同，可以返回 true。

如果删掉等长检查，这个推理就不成立，例如 s 为 `"ab"`、t 为 `"a"`，扣减未出现负数但仍有 b 剩余。

两个循环的下标都单调递增且有长度上界，因此算法能够终止。

## 8. 复杂度及方案对比

长度不等时先返回 false，耗时 O(1)、额外空间 O(1)。下面讨论长度相等的情况，n 为字符串长度，C 为字符集大小。

| 方案 | 时间复杂度 | 额外空间 | 优势 | 代价或限制 |
| --- | --- | --- | --- | --- |
| 暴力逐个匹配 | 最坏 O(n²) | O(n) | 直观，能直接模拟一一配对 | 重复扫描已处理位置 |
| 排序后比较 | 通常 O(n log n) | 至少 O(n) 的字符数组副本 | 排序后表示统一，思路通用 | 需要复制和排序，排序辅助空间另取决于实现 |
| 通用哈希计数 | 平均 O(n) | O(k)，k 为不同字符数 | 可适应较大、动态字符集合 | 哈希操作有额外开销，平均复杂度有前提 |
| 本题固定数组计数 | O(n + C) | O(C) | 单次统计与抵消，直接寻址，无哈希冲突 | 依赖可映射的小字符集合 |

本题 C 固定为 26，数组初始化为常数成本，两次顺序遍历至多处理 2n 个字符，所以时间可简写为 O(n)，额外空间为 O(1)。代码通过 `charAt` 读取字符串，不创建字符数组副本。

频次最大为 50000，int 能安全保存。不要用 byte 等容量不足的类型记录数量。

对结果为 true 的一般输入，需要读取所有字符才能排除最后一个字符不同的可能，因此最坏情况下仍需线性读取；当前方案已达到该输入模型下合理的时间复杂度量级。它的价值不是“没有内存成本”，而是将与长度有关的匹配状态压缩成固定的 26 个计数。

## 10. Unicode 进阶：先确定“字符”是什么意思

Unicode 字符远超 26 个，不能继续直接使用 `character - 'a'`。可以改为 `Map<Integer, Integer>`，以 Unicode 码点作为键，保存频次；Java 可通过 `String.codePoints()` 按码点遍历。

注意 Java 的 char 是一个 UTF-16 代码单元，部分字符（如许多 emoji）由两个 char 组成。按 `charAt` 或 `Map<Character, Integer>` 计数，得到的是代码单元的频次，不能直接当作码点频次。

扩展版本应按码点数量与频次判断，而不是照搬以 `String.length()` 为字符数量的论证。如果产品将组合重音字符与预组合字符视为相同，还要明确是否先做 Unicode 规范化；用户看到的一个字形也可能由多个码点组成，这又涉及字素簇。不要在未定义语义时擅自忽略大小写、重音或空格。

本次仅讨论扩展思路，没有实现或声称验证 Unicode 版本。

## 11. 边界情况与常见错误

| source | target | 预期 | 检查目的 |
| --- | --- | --- | --- |
| `anagram` | `nagaram` | true | 官方正例 |
| `rat` | `car` | false | 官方反例 |
| `aab` | `aba` | true | 重复字符重排 |
| `aab` | `abb` | false | 种类相同，频次不同 |
| `ab` | `ba` | true | 中途差值不等不一定意味着最终不等 |
| `ab` | `a` | false | 等长检查不可遗漏 |
| `a` | `a` | true | 最短合法长度、相同字符串 |
| `a` | `b` | false | 最短不同字符 |
| `az` | `za` | true | 映射端点 0 和 25 |
| `ad` | `bc` | false | 编码和相同不代表频次相同 |
| 空字符串 | 空字符串 | true | 仓库扩展 |
| 空字符串 | `a` | false | 仓库扩展 |

常见错误：遗漏长度检查；只比较字符种类或编码总和；暴力匹配忘记标记位置；减计数前就检查负数；同步增减却在中途负数时提前返回；将固定数组解法误用于整个 Unicode 字符集。
